# Performance

Run `composer benchmark` or `php tools/benchmark.php --write`. The latter records docs/benchmark-results.json. Inputs are 100 B, 1 KiB, 10 KiB and 100 KiB; dictionaries contain 100, 1,000, 10,000 and 100,000 synthetic shared-prefix terms. Each case has five warmups and 100 samples. Compilation is measured separately. The naive baseline runs five raw strpos-per-term passes; it performs less work than the full normalization/evidence/policy engine, so it is illustrative rather than an equivalent implementation comparison.

The review run used macOS arm64, PHP 8.5.8, ICU 78.3. At 10,000 terms and 10 KiB, clean/matched p50 was 0.84/1.876 ms, p95 1.022/2.027 ms, p99 1.168/2.351 ms; compilation was 51.712 ms. At 100,000 shared-prefix terms, compilation was 470.888 ms, allocator growth 63012864 bytes and whole-process peak 112328704 bytes. Allocator reuse can produce a zero small-dictionary delta. These are synthetic engine measurements, not production promises.

The pure engine makes zero SQL/network calls. Those numbers exclude WordPress hooks, policy reads, object-cache serialization and audit writes. Therefore the requested p50/p95/p99 WordPress overhead targets have NOT been established. Dictionary compilation and missing persistent caching can exceed hot-path targets. Admin editor limits 1,000 terms; portable policy format limits 10,000, even though the pure matcher benchmark supports 100,000 shared-prefix entries. Compiled dictionaries are additionally bounded to 2 MiB normalized patterns and 200,000 trie states; large arbitrary unique dictionaries can be rejected before reaching 100,000 terms. Compilation periodically checks PHP memory headroom; persistent-cache deserialization overhead remains an unresolved risk.

Policy snapshots are loaded lazily and compiled once per request/site. Version/checksum/prefix-aware object cache keys permit reuse with persistent caching. A default WordPress memory cache cannot persist across requests. Object-cache-on/off matrix and Redis/Memcached serialization/transfer overhead remain unmeasured. Word boundaries and output limits protect matching; rule predicates are separately bounded to 256 rules of 128 nodes each. More adversarial worst-case memory/time tests are required.

Retention performs at most five 1,000-event batches per callback, then schedules a continuation if the batch remained full. A 5,501-row backlog was drained across two callbacks in the isolated integration test. Configurable throughput, scheduler-independent guarantees and background recovery remain outstanding. Audit pagination uses keysets; privacy exports use bounded actor/creator pages under WordPress's callback contract. Large-user export profiling remains outstanding.

Review changes bound exception windows/source-map edits and cache field/type matcher subsets. HTML/link extraction uses local DOM parsing; nesting over 128 requires review. The recorded 32-case benchmark uses text fields and does not establish HTML/exception-heavy latency or persistent-cache overhead.
